# DDD项目

Java 的 DDD（Domain-Driven Design，**领域驱动设计**）项目，是指**以业务领域为核心**来组织代码结构、业务逻辑和软件架构的 Java 应用程序。 

与传统以数据库表为中心的 CRUD（增删改查）或 MVC 架构不同，DDD 项目强调业务逻辑应该放在最核心的位置，而不是受限于数据库怎么建或框架怎么写。

一、 核心特点与设计思想

- **以业务为中心**：开发团队、产品经理和业务专家使用同一套**通用语言**（Ubiquitous Language）来定义业务概念，确保代码中的类名、方法名直接反映业务含义。
- **解耦业务与技术**：核心的业务逻辑不依赖 Spring、MySQL 等具体技术框架。
- **高内聚、低耦合**：将复杂的业务拆分成多个子域和**限界上下文**（Bounded Context），非常契合微服务架构。

二、 典型的 Java DDD 四层架构

在代码落地时，DDD 项目通常采用以下经典分层（从外到内或从上到下）：

1. **Interface（用户接口层 / 表现层）**
   - 负责接收前端或外部系统的请求。
   - 进行参数校验、数据转换（如 VO 与 DTO 互转），调用应用层。
2. **Application（应用层）**
   - 负责用例和流程的编排（如：用户下单流程：扣库存 -> 生成订单 -> 发送通知）。
   - 不包含复杂的业务规则，只负责“调度”。
3. **Domain（领域层 —— 核心）**
   - **整个项目最核心的地方**，封装了所有的业务规则和逻辑。
   - 包含以下核心概念：
     - **实体（Entity）**：有唯一标识的对象（如：订单 ID 对应的 Order）。
     - **值对象（Value Object）**：无唯一标识、不可变的属性集合（如：地址、经纬度）。
     - **聚合与聚合根（Aggregate / Aggregate Root）**：一组相关对象的集合，由聚合根统一对外暴露行为，保证数据一致性。
     - **领域服务（Domain Service）**：处理不属于某个单一实体或值对象的业务逻辑。
     - **仓储接口（Repository Interface）**：只定义“保存/获取聚合”的契约，不涉及具体实现。 [[1](http://www.joysenergy.com/product/11.html)]
4. **Infrastructure（基础设施层）**
   - 提供最底层技术支持。
   - 实现领域层定义的仓储接口（如用 MyBatis 连 MySQL、用 Redis 做缓存、调用第三方 HTTP 接口等）。

三、 传统 MVC 与 DDD 项目的对比

| 维度               | 传统 MVC 项目 (贫血模型)                      | Java DDD 项目 (充血模型)                     |
| ------------------ | --------------------------------------------- | -------------------------------------------- |
| **驱动力**         | 数据库表结构驱动（先设计表，再写 Service）    | 业务领域模型驱动（先理解业务，再建领域模型） |
| **业务逻辑存放处** | 大量堆积在各种 `XxxServiceImpl` 中            | 封装在**领域对象（实体/领域服务）**中        |
| **对象特点**       | 贫血对象（只有 getter/setter 属性，没有行为） | 充血对象（属性与操作业务的方法结合在一起）   |
| **适用场景**       | 业务逻辑简单、快速迭代的增删改查系统          | 业务极其复杂、长期演进的大中型企业级系统     |
